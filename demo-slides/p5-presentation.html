Motivation

Why Hybrid? No Single Retriever Wins Everything

SQL only
  • Handles structured attributes perfectly — gender, price, stock
  • Fails on natural language: "cozy winter jacket" returns 0 rows — column says "puffer", not "cozy"
  • No ranking — returns all matches equally
BM25 only
  • Fast keyword matching — "kurta" finds every kurta in the catalogue
  • Fails on synonyms — "ethnic suit" misses "anarkali" if neither word appears in query
  • Ignores structured filters — surfaces men's kurtas when you asked for girls
Vector only
  • Understands meaning — "yoga pants" matches "wide-leg palazzo" semantically
  • Fails on exact keyword queries — "lion print t-shirt" needs BM25 precision
  • No structural awareness — "under ₹500 in stock" needs SQL

Solution: Run all three in parallel, then merge using RRF. Each retriever contributes what it does best. No score calibration needed. See mcp_server.py:79 — pool_k = top_k * 4 if filters else top_k * 2.

Step 1

LLM Query Decomposer

Why decompose at all?

A user query like "white cotton dress for girls under ₹500 in stock" contains two kinds of intent: semantic description (for vector/BM25) and structured constraints (for SQL). Mixing them into a single BM25 query degrades both. Separating them lets each retriever do exactly what it's built for.

Design decisions

  • Temperature=0 — decomposer must be deterministic, not creative
  • No category key — DB category column stores item types ("pants", "dress"), not demographic groups. Removed from schema after eval showed it caused WHERE category='women' → 0 rows
  • Age range rules — "for kids" → max_age=12; "for teens" → min_age=13, max_age=17
  • Fallback — any JSON parse error → {semantic_query: rawQuery, filters: {}}

decomposer.py system prompt (key rules)

# Only valid filter keys:

colour    : lowercase colour name

min_age   : integer (years)

"for teens"    → min_age=13, max_age=17

Steps 2–4

Three Retrievers — Each One Specialised

SQL Filtersql_filter.py
  • Builds parametric WHERE clause from any filter combination
  • All conditions AND-ed — only exact matches qualify
  • psycopg2.extras.RealDictCursor → list of dict rows
  • ORDER BY price ASC — cheapest first for SQL leg

BM25 Keywordbm25_retriever.py
  • BM25Okapi index built at module import on all 65 products
  • Corpus = name + description, tokenised with re.findall([a-z0-9]+)
  • Stays in memory — zero latency after startup
  • Zero-score results excluded — only real keyword matches surface
# bm25_retriever.py: tokenize + search
def _tokenize(text):
  return re.findall(r"[a-z0-9]+",
                     text.lower())

scores = _bm25.get_scores(tokens)
# zip with product list, exclude 0s
pgvectorvector_retriever.py
  • Query embedded with input_type="query" vs "passage" at ingest — different prompt prefixes
  • 2048-dim vectors (nvidia/nv-embedqa-e5-v5)
  • Cosine similarity via PostgreSQL <=> operator
  • similarity = 1 - (embedding <=> vec)
# vector_retriever.py: cosine search
SELECT *, 1 - (embedding <=> %s::vector)
  AS similarity
FROM products
ORDER BY embedding <=> %s::vector
LIMIT %s

Key constraint: SQL retriever gets the structured filters dict. BM25 and vector get the semantic_query string. Different inputs for different strengths — this is the whole point of the decomposer.

Step 5

RRF Merge — Rank Without Score Calibration

The problem with raw score merging

BM25 returns scores like 7.23. pgvector returns cosine similarity like 0.87. SQL has no score at all. You can't add these — they live in completely different scales. Calibrating them requires expensive experiments that need repeating whenever you change any retriever.

RRF: use rank, not score

Every item that appears in any retriever list gets a contribution of 1 / (60 + rank). The 60 is the smoothing constant from the original RRF paper — it dampens the advantage of rank 1 vs rank 5. An item appearing in all three lists scores much higher than an item appearing in just one.

merger.py — the full implementation

# merger.py — RRF formula
_K = 60  # RRF smoothing constant

for ranked in ranked_lists:
  for rank, product in enumerate(ranked, start=1):
    pid = product["id"]
    rrf_scores[pid] = (
      rrf_scores.get(pid, 0.0)
      + 1.0 / (_K + rank)   # ← line 38
    )

# Sort descending by combined RRF score
sorted_ids = sorted(rrf_scores,
  key=lambda pid: rrf_scores[pid],
  reverse=True
)

Example: product at SQL rank 3 + BM25 rank 1 + vector rank 5 gets:
1/63 + 1/61 + 1/65 = 0.0477 — higher than a product that only appears in one list at rank 1 (1/61 = 0.0164).

Step 6 — Design Decision

Post-RRF Hard Filter: Fixing BM25's Demographic Blindness

The failure mode

Query: "ethnic kurta for girls".

BM25 finds every product with "kurta" in its name — which are all men's and women's kurtas. They rank #1–#4 in the BM25 leg. The correct item (Yellow Anarkali Suit, gender=girls, ID 23) has no "kurta" in its description — BM25 misses it entirely. After RRF merge, the men's/women's kurtas dominate because they appear in BM25 and vector. Hybrid P@5 = 0.00.

The fix: post-RRF gate

After RRF merge over an expanded 4× pool, apply hard demographic filters. If gender=girls is in the decomposed filters, drop every non-girls item from the merged results. With non-girls kurtas gone, ID 23 surfaces. Hybrid P@5 = 0.20.

mcp_server.py — _hard_filter()

# mcp_server.py:33-50
def _hard_filter(products, filters):
  """Gender + in_stock as hard gates.
  Unisex satisfies any gender request."""
  out = []
  gender_want = str(filters.get("gender","")).lower()
  stock_needed = filters.get("in_stock") is True

  for p in products:
    if gender_want:
      pg = p.get("gender","").lower()
      if pg != gender_want and pg != "unisex":
        continue   # drop wrong gender
    if stock_needed and not p.get("in_stock"):
      continue
    out.append(p)
  return out

Why only gender + in_stock? These are demographic/availability constraints — if you say "for girls", a women's item is genuinely wrong. Colour and fabric are preferences — showing a georgette dress when you asked for cotton is a near-match, which is useful. Those stay soft.

Unisex pass-through: A unisex hoodie satisfies "fleece hoodie for men". Without this, ID 31 (Oversized Cozy Hoodie, unisex) was incorrectly dropped, hurting Q13 P@5.

Steps 7–8

MCP Tool + LangGraph ReAct Agent

FastMCP

Entire pipeline as one tool

  • The 7-step pipeline is wrapped as a single @mcp.tool() — the agent calls search_products(query, top_k) and gets back JSON with decomposed filters + results
  • Agent doesn't need to know about SQL, BM25, vector, or RRF — that complexity is behind the tool boundary
  • In-process bridge: agent imports search_products directly — no subprocess, no network hop
# mcp_server.py:53-112
@mcp.tool()
def search_products(query: str,
                    top_k: int = 10) → str:
  decomposed = decomposer.decompose(query)
  pool_k = top_k * 4 if filters else top_k * 2
  sql = sql_filter.search(filters, pool_k)
  bm25 = bm25_retriever.search(sem_q, pool_k)
  vec = vector_retriever.search(sem_q, pool_k)
  merged = merger.merge(sql, bm25, vec, pool_k)
  return json.dumps({"decomposed":...,"results":...})
LangGraph

ReAct agent with backoff

  • LangGraph ReAct loop: agent_node → tool_node → should_continue → …
  • System prompt: "Call search_products EXACTLY ONCE per request" — prevents the agent from being over-agentic and calling 3× (was observed before the instruction was added)
  • 4-attempt exponential backoff: 5s → 10s → 20s for NVIDIA 429 overload errors
  • SSE events streamed to frontend: tool_call → tool_result → final_answer → done
# agent.py: LangGraph state machine
workflow.add_node("agent", agent_node)
workflow.add_node("tools", tool_node)
workflow.add_conditional_edges(
  "agent",
  should_continue,  # checks last msg for tool_calls
  {"tools": "tools", "end": END}
)

eval/run_eval.py — precision formula

# eval/run_eval.py:45-50
def precision_at_k(results, expected_ids, k):
  if not expected_ids: return -1.0
  top_ids = [r["id"] for r in results[:k]]
  hits = sum(1 for pid in top_ids
             if pid in expected_ids)
  return hits / min(k, len(top_ids))
Design Decisions

Five Decisions That Shaped the System

Decision 1

Remove category from decomposer

Initial decomposer extracted category="women" from "yoga pants for women" but the DB category column stores item types like "pants" and "dress", not demographic groups. WHERE category='women' returned 0 rows. Removing category from the schema fixed Q4 from 0.40→0.60.

Decision 2

Adaptive pool size vs fixed

First attempt used a flat 4× pool for all queries. Open queries (no filters) got 40 items per retriever, which diluted the RRF merge and hurt Q9 (0.60→0.40). Fix: pool_k = top_k * 4 if filters else top_k * 2 — expanded pool only when post-filtering will reduce results.

Decision 3

Unisex items pass any gender filter

First hard-filter version dropped ID 31 (Oversized Cozy Hoodie, gender=unisex) when the user searched "for men". A unisex item is a valid result for any gender request. Added: if pg != gender_want and pg != "unisex": continue.

Decision 4

In-process MCP bridge

FastMCP supports HTTP and stdio transports for multi-process use. For this single-machine setup, the agent directly imports search_products from mcp_server.py — no subprocess, no port, no serialisation overhead. Same MCP tool interface, zero latency on the bridge.

Decision 5 — Mismatch UI is a product decision, not just an engineering one

Returning near-matches when no exact match exists is the right search behaviour — showing nothing is worse than showing the closest thing. But the UI must be honest about which attributes don't match. computeMismatches() in page.tsx:53 diffs product attributes against decomposed filters entirely client-side. The backend sends all data; the frontend interprets it. No API change needed.
