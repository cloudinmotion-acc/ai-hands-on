Title — Hybrid Product Search
~1 min  ·  Orientation
Say

P5 is the most technically complex phase in this portfolio — it combines three completely different retrieval strategies and merges them into a single ranked output. Everything you see on the screen — the product cards, the mismatch badges, the streaming answer — is produced by a 7-step pipeline that runs on every query.

Frame for the audience

This isn't a demo of a product search box. It's a systems demo of how you build retrieval when you can't afford for any single approach to be a single point of failure. The product search domain is just an easy-to-understand vehicle for the underlying architecture.

Timing note

Start the timer now. Slide 1 should take no more than 60 seconds — you're just setting context, not explaining anything yet.

Why Hybrid? Single Retriever Failures
~2 min  ·  Motivation
Say

Let me show you what happens when you use just one retriever. These aren't hypotheticals — each of these failures is directly observable from the eval data.

  • SQL only: "cozy winter jacket" → 0 rows. The catalogue says "puffer jacket". SQL does exact column matching — it can't handle synonym drift.
  • BM25 only: "ethnic kurta for girls" → surfaces men's kurtas. BM25 finds everything with "kurta" in the name, and there are more men's kurtas than girls'. It doesn't know gender matters.
  • Vector only: "lion print t-shirt for kids" → wrong item. "Lion print" is specific enough that BM25 precision matters more than semantic understanding.
Key insight to land

Each retriever has a different failure mode: SQL fails on language, BM25 fails on intent, vector fails on specificity. The only way to handle all three is to combine them. That's the architecture we built.

Code reference if asked

The adaptive pool size logic is in mcp_server.py:79:

pool_k = top_k * 4 if filters else top_k * 2

This is the implementation evidence that we thought carefully about how these retrievers interact — not just that they run together.

7-Step Pipeline Architecture
~2 min  ·  Overview
Say

Every user query goes through exactly these 7 steps. Steps 2–4 are functionally parallel — they all get input from step 1 but don't depend on each other.

  • Step 1: Decomposer (LLM splits query into semantic + structured parts)
  • Steps 2–4: SQL + BM25 + vector all run on the expanded pool
  • Step 5: RRF merges the three ranked lists
  • Step 6: Hard filter gates out wrong-gender items
  • Step 7: LangGraph agent wraps everything, streams answer via SSE
File map for technical audience

Point to each box and name the file:

  • Decomposer → search/decomposer.py
  • SQL filter → search/sql_filter.py
  • BM25 → search/bm25_retriever.py
  • pgvector → search/vector_retriever.py
  • RRF merge → search/merger.py
  • Hard filter + orchestration → mcp_server.py
  • Agent → agent.py
Don't get lost here

This slide is just orientation. You'll explain each component on subsequent slides. Don't spend more than 2 minutes — just give people the mental map so they know where they're going.

4
LLM Query Decomposer
~2 min  ·  Technical depth
Say

The decomposer is the first LLM call in every pipeline execution. It takes the raw user query and splits it into two outputs: a semantic query — clean natural language for BM25 and vector — and a filters dict with structured key-value pairs for SQL.

For "white cotton dress for girls under ₹500 in stock", it returns semantic_query "white cotton dress" and filters with colour=white, fabric=cotton, gender=girls, max_price=500, in_stock=true.

Why this matters technically

The naive approach is to pass the full query to all three retrievers. But if you send "comfortable yoga pants for women in stock under ₹800" to BM25, the stop words and price clause degrade the score. The decomposer strips exactly what each retriever doesn't need.

Code reference — decomposer.py:41-64

The system prompt bans the category key explicitly:

"Do NOT include a 'category' key — it is not a valid filter."

This rule was added after the eval showed WHERE category='women' returning 0 rows — the DB column stores item types like "pants" not demographic groups. This is an example of eval-driven prompt iteration.

Code reference — decomposer.py:86-100

Defensive parsing — strip markdown fences if LLM wraps JSON, then fallback to raw query if JSON parse fails:

if raw.startswith("```"):
    raw = raw.split("```")[1]
    if raw.startswith("json"):
        raw = raw[4:]
# fallback if anything fails
return {"semantic_query": query, "filters": {}}

Temperature=0 here — the decomposer must be deterministic. You're using it as a structured parser, not a creative generator.

5
Three Retrievers
~2.5 min  ·  Technical depth
SQL — say

SQL filter takes the structured filters dict and builds a parametric WHERE clause. All conditions are AND-ed — it's an exact match against structured columns. It gets the structured filters, not the semantic query.

Code reference — sql_filter.py:43-73 
if gen := filters.get("gender"):
    conditions.append("LOWER(gender) = LOWER(%s)")
    params.append(gen)
if (mx := filters.get("max_price")):
    conditions.append("price <= %s")
    params.append(int(mx))

Parametric queries — no string formatting, no injection risk.

BM25 — say

BM25 index is built on all 65 products at module import — name plus description concatenated, tokenized to [a-z0-9]+ tokens. It stays in memory. Zero latency after startup. Items with BM25 score of exactly 0 are excluded — they're not real keyword matches.

Code reference — bm25_retriever.py 
def _tokenize(text):
    return re.findall(r"[a-z0-9]+", text.lower())

scores = _bm25.get_scores(tokens)
# zip with product list, exclude 0s
Vector — say

pgvector with NVIDIA's nv-embedqa-e5-v5 model — 2048 dimensions. The distinction between input_type="passage" at ingest vs "query" at search time is important — these models use different prompt prefixes for each mode. Cosine similarity via the <=> operator in PostgreSQL.

Anticipate this question

If asked "why 2048 dimensions": that's the model's native dimensionality. More dims = better retrieval quality at the cost of storage and distance computation. We use it because NVIDIA NIM hosts it and it's available via our API key.

6
RRF Merge
~2.5 min  ·  Algorithm
Say

The core insight of RRF is that you don't need calibrated scores to merge ranked lists. You only need ranks. Each item gets a contribution of 1 / (60 + rank) from each list it appears in. The 60 is the smoothing constant from the original Cormack 2009 paper — it dampens the difference between rank 1 and rank 5, so you don't get all-or-nothing behavior at the top.

Code reference — merger.py:38 
_K = 60  # RRF smoothing constant

for rank, product in enumerate(ranked, start=1):
    pid = product["id"]
    rrf_scores[pid] = (
        rrf_scores.get(pid, 0.0)
        + 1.0 / (_K + rank)
    )
Explain with numbers

A product that appears in all three lists at rank 3, 1, and 5:

1/(60+3) + 1/(60+1) + 1/(60+5) = 0.0159 + 0.0164 + 0.0154 = 0.0477

A product that only appears in BM25 at rank 1:

1/(60+1) = 0.0164

The multi-list product scores 2.9× higher — it's validated by multiple evidence sources. That's the key property of RRF.

Why not learned rank fusion?

Learned rank fusion (like LambdaRank or Reciprocal Rank Fusion with learned weights) requires training data with relevance labels. We have 15 labelled queries — that's not enough. RRF is unsupervised and works well from day zero. You'd switch to learned fusion once you have thousands of logged queries with user click signals.

7
Post-RRF Hard Filter
~2 min  ·  Design decision
Say — the failure first

Q11: "ethnic kurta for girls". Before this fix, hybrid P@5 was 0.00. Here's exactly what went wrong: BM25 finds all products with "kurta" in name or description — there are six, all men's or women's. They rank #1–#4 in BM25. The only girls item, Yellow Anarkali Suit (ID 23), doesn't have "kurta" in its description — it's an anarkali. BM25 never sees it. Vector gives it a moderate score but men's kurtas still dominate the RRF merge because they appear in BM25 AND vector. After RRF: men's kurtas at positions 1–4, girls item nowhere in top 5.

Say — the fix

The solution is to apply a hard demographic gate after RRF, not before. We merge 40 items (4× pool), then drop everything that doesn't match the requested gender. With men's and women's kurtas gone, ID 23 surfaces. P@5 goes from 0.00 to 0.20.

Code reference — mcp_server.py:33-50 
def _hard_filter(products, filters):
    gender_want = str(filters.get("gender", "")).lower()
    stock_needed = filters.get("in_stock") is True
    for p in products:
        if gender_want:
            pg = p.get("gender", "").lower()
            if pg != gender_want and pg != "unisex":
                continue  # drop wrong gender
        if stock_needed and not p.get("in_stock"):
            continue
        out.append(p)
Explain the soft/hard distinction

Gender and in_stock are hard gates — showing a men's item when you asked for girls is a wrong result, full stop. Colour and fabric are soft — showing a cotton dress when you asked for silk is a near-match, which is better than showing nothing. The mismatch UI (slide 9) handles the communication gap for soft mismatches.

The unisex edge case

Without pg != "unisex" in the condition, ID 31 (Oversized Cozy Hoodie, unisex) got dropped when the user searched "fleece hoodie for men". A unisex item is a valid result for any gender. This is the kind of edge case you only find by running eval against real data.

MCP Tool + LangGraph ReAct Agent
~2 min  ·  Agentic layer
Say — MCP

The entire 7-step pipeline is wrapped as a single MCP tool: search_products(query, top_k). The LangGraph agent doesn't know about SQL, BM25, vector, or RRF. It just calls one tool and gets back a JSON payload with decomposed filters and results. That's the MCP value proposition — complexity behind a clean tool interface.

Code reference — mcp_server.py:53 
@mcp.tool()
def search_products(query: str, top_k: int = 10) -> str:
    decomposed = decomposer.decompose(query)
    # ... pool sizing, three retrievers, RRF, hard filter ...
    return json.dumps({"decomposed": decomposed, "results": merged})

In-process bridge: the agent file directly imports search_products from mcp_server.py — no subprocess, no port, no serialisation round-trip. Same MCP tool interface as if it were running over stdio or HTTP, but zero added latency.

Say — LangGraph

The agent is a LangGraph ReAct state machine: agent_node checks if there are tool_calls in the last message. If yes, ToolNode executes them. should_continue decides whether to loop back or end. The system prompt says "call search_products EXACTLY ONCE per request" — this was necessary because without it, the model would call the tool twice then synthesize.

4-attempt backoff — why

NVIDIA NIM returns HTTP 429 under load. The agent_node retries up to 4 times with exponential backoff: 5s → 10s → 20s. Without this, the entire request fails on the first NVIDIA overload spike. The code is in agent.py inside the try/except around llm.invoke().

SSE Streaming + Mismatch UI
~2 min  ·  Frontend + UX
Say — SSE

The frontend receives four SSE event types in sequence as the agent runs: tool_call → shows a spinner with the tool name; tool_result → shows decomposed filters and product cards; final_answer → streams the AI text; done → stops the spinner. The user sees products before the AI finishes writing its answer.

Code reference — main.py SSE events 
data: {"type":"tool_call", "tool":"search_products", ...}
data: {"type":"tool_result", "decomposed":{...}, "top_results":[...]}
data: {"type":"final_answer", "content":"..."}
data: {"type":"done"}
Say — mismatch badges

The mismatch highlighting is a pure frontend feature. The tool_result event already contains both the decomposed filters and each product's attributes. computeMismatches() diffs them client-side. If a product's fabric doesn't match the searched fabric, the badge turns amber with a warning icon. No backend change was needed — the data was already there.

Code reference — page.tsx:53-79 
if (filters.fabric && s(product.fabric) !== s(filters.fabric))
    mismatches.add("fabric");  // → amber badge

if (filters.gender) {
    const pg = s(product.gender);
    if (pg !== s(filters.gender) && pg !== "unisex")
        mismatches.add("gender");
}
The UX design rationale

Returning near-matches when no exact match exists is the right retrieval behaviour — showing nothing is worse. But showing a cotton blouse in response to "silk blouse" without telling the user it's cotton is misleading. The amber badge says: "we know this isn't perfect, here's why." That's product integrity.

Eval Results — Precision@5
~2 min  ·  Numbers
Say

15 queries across 3 retrieval modes. Precision@5 is the fraction of the top-5 results that are expected matches — denominator is min(5, actual result count) so we don't penalise for catalogue gaps. BM25 averages 0.28, vector 0.32, hybrid 0.32. Hybrid matches vector precision but adds structural filter enforcement that vector-only can't provide.

Code reference — eval/run_eval.py:45 
def precision_at_k(results, expected_ids, k):
    top_ids = [r["id"] for r in results[:k]]
    hits = sum(1 for pid in top_ids if pid in expected_ids)
    return hits / min(k, len(top_ids))
Explain the key results
  • Q4 (yoga pants for women in stock): No "yoga pants" in catalogue. Hybrid scores 0.60 — vector understands "yoga pants" → "elasticated wide-leg pants" even without the exact keyword
  • Q11 (ethnic kurta for girls): 0.00 → 0.20 after post-RRF hard filter. The fix is visible in the numbers.
  • Q2 (lion print t-shirt for kids): BM25 = 1.00. Exact keyword match — BM25 wins when the text is there.
  • Q8 (kids under ₹300): SQL = 1.00. Pure structured query — SQL wins when you need exact numeric filtering.
Anticipate "why only 0.32?"

Many queries have only 1 expected item in the catalogue (Q2, Q3, Q5, Q7, Q11, Q14, Q15). Finding that one item in top-5 gives P@5 = 0.20 — that's the theoretical max for those queries. The system is performing correctly; the eval numbers just reflect catalogue coverage. A richer catalogue would show higher absolute scores.

Five Design Decisions
~1.5 min  ·  Reflection
Say

Every system has decisions that look obvious in hindsight. These five weren't — they came out of debugging eval failures.

  • Remove category from decomposer: Eval showed WHERE category='women' → 0 rows. The DB column stores item types, not demographics. Fixed Q4 from 0.40 to 0.60.
  • Adaptive pool sizing: Flat 4× pool for all queries hurt open queries like "floral print summer dress" — too many items competing in RRF. Adaptive: 4× with filters, 2× without.
  • Unisex pass-through: Hard filter initially dropped unisex items. An oversized hoodie for everyone is a valid result for "hoodie for men". One line fix.
  • In-process MCP bridge: Direct import instead of subprocess. Zero latency overhead on the tool call boundary. Same interface if you ever want to move to HTTP transport.
  • Mismatch UI as product integrity: The decision to show near-matches AND flag them is a product decision, not just engineering. It's honest retrieval.
Framing for interview

The through-line across all five decisions is: eval-driven iteration. You set up an eval, ran it, found failures, fixed them, re-ran. That loop — not the initial architecture — is what produces a reliable system. The architecture is a starting hypothesis. The eval tells you where it's wrong.

Q&A — Likely Questions
~3 min  ·  Discussion
Anticipated Questions
How does RRF compare to a learned ranking model like LambdaRank?
Learned ranking is better when you have thousands of labelled query-result pairs with click signals. We have 15 labelled queries — not enough. RRF is unsupervised and works from day zero. In production at scale, you'd collect user interaction data for 3–6 months, then train a ranker on top of the RRF output. RRF stays as a baseline to beat.
Why use MCP if it's just one tool and one agent?
Two reasons: (1) The tool boundary lets you swap the backend completely — you could replace the SQL+BM25+vector pipeline with a different approach without changing any agent code. (2) If you add more tools later (cart, order history, recommendations), the agent already speaks MCP — no refactor. It's an interface investment.
What would you change if this went to production?
Three things: (1) Async BM25 refresh — currently the index is built at startup and never updated. A cron job or PostgreSQL trigger would rebuild it when products change. (2) pgvector HNSW index — currently linear scan over 65 items. For 100K+ products, you need an approximate nearest-neighbour index (CREATE INDEX ON products USING hnsw (embedding vector_cosine_ops)). (3) Replace httpx.Client(verify=False) with the Accenture CA bundle — that's a corporate proxy workaround, not production-safe.
Why is the decomposer temperature=0 but the agent model temperature is higher?
The decomposer is a parser — it must produce deterministic, well-formed JSON. Temperature=0 eliminates sampling variance. The agent needs to write natural language answers — some creative variation is fine and even desirable. Temperature=1 for gpt-oss-20b judge in the P3 eval was a RAGAS quirk; here the agent uses the default nemotron temperature setting.
How do you handle queries where the catalogue genuinely has nothing relevant?
The hard filter has a fallback: if len(filtered) < max(1, top_k // 4), we return the unfiltered RRF results rather than an empty list. The mismatch badges then flag that the results don't fully match the query. The agent's final answer synthesizes this honestly — "we don't carry silk blouses under ₹800, here's the closest we have."
Closing

End with: "The key engineering lessons from P5 are: no single retriever handles all query types, RRF gives you a principled way to merge them without score calibration, and an automated eval loop is how you find the edge cases before your users do."
