P1 — Invoice Extractor

The Problem: Invoice Hell

"Businesses receive invoices in every format — PDFs, scanned images, thermal receipts, multi-page bills. Someone manually keys in 8 fields per invoice. Errors compound. Audits are painful."
  • Traditional OCR gives you text, not structure
  • Template matching breaks on new vendor formats
  • Manual keying has a 1–5% per-field error rate
  • Vision LLM reads and understands in one step — no preprocessing

8 Fields. One LLM call.

{
  "invoice_no":     "INV-2026-001",
  "vendor_name":   "Raju Gari Biryani",
  "date":          "2026-01-18",    ← normalised
  "total":         450.00,
  "subtotal":      381.36,
  "tax":           68.64,          ← GST combined
  "payment_method":"UPI",
  "gstin":         "29AAACC1206D1ZM"
}

Date normalised to ISO 8601 regardless of input format. Null for absent fields — never a guess.

Step 1 — Read

  • Convert each PDF page to JPEG via pdf2image
  • Base64-encode for multimodal API transport
  • Handles multi-page invoices natively

Steps 2 + 3 — Extract & Verify

  • LLM reads image → outputs raw JSON
  • Second LLM call: "look again, verify every field"
  • Self-verification catches ~8% of edge-case errors
  • 3 retries: exponential backoff 1s → 2s → 4s

Step 4 — Validate

  • Pydantic v2 schema enforcement — types guaranteed
  • Date normalizer: any format → YYYY-MM-DD
  • Amounts → Decimal (no float rounding drift)
  • Missing = null, never fabricated

Why two LLM calls? Separating extraction from verification is the same as having someone else proofread your work. First it reads, then it checks — both focused on one task. This is test-time compute: spend more inference for better accuracy.

Why does CoT win?
The model reasons step-by-step before committing — distinguishes "Estimate No" from "Invoice No", finds totals hidden in multi-section receipts, and checks whether subtotal + tax = total.

v5 Strict performs worst — why?

Over-constraining with rigid rules makes the model defensive. It returns null for fields it could have inferred — the opposite of what we want. Explicit rules can't cover every invoice format; the model's internal reasoning handles variability better.

Remaining failure mode: GSTIN

15-character alphanumeric codes — one transposed digit is a wrong GSTIN. Post-processing fix: GSTIN checksum validator (mod-11 algorithm). We know the fix — deliberate scope decision not to implement it.

Eval is automated, not manual

eval.py runs all 5 prompt versions against 4 real invoices with field-by-field comparison against ground_truth.json. Accuracy is a reproducible number, not a vibe check.

P2 — RAG Assistant

Why RAG? The Hallucination Problem.

Without RAG

You ask: "What's our annual leave policy?"

The LLM answers confidently. It's generating the most plausible-sounding text from training memory. It's probably wrong. It never says "I don't know." That's hallucination.

With RAG

You upload your policy document. The LLM answers only from the text you provided, and cites the exact paragraph it used. If the answer isn't there, it says so explicitly.

"Think of it like an open-book exam. Without RAG, the LLM is doing a closed-book exam from memory. With RAG, you put the textbook in front of it and say: answer only from this."

What it unlocks for enterprise

  • Grounded answers — every claim traceable to a source chunk
  • Private data — documents never leave your infrastructure
  • Always current — update the document, update the knowledge instantly
  • Explicit refusal — "I could not find this in the provided documents"
  • Multi-format support — PDF, Excel, TXT in one pipeline

Chunking Strategy

  • 500 chars per chunk — dense prose sweet spot
  • 50-char overlap — no key sentence lost at boundaries
  • RecursiveCharacterTextSplitter — respects paragraph & sentence breaks
  • Excel: 10 rows per chunk, column headers preserved

Smaller = precise retrieval. Larger = richer context per chunk. 500/50 is the production default.

Embedding Model

  • nvidia/nemotron-3-embed-1b
  • 1024-dimensional dense vectors
  • Semantic search — finds meaning, not keywords
  • Same model at ingest AND query time

Mixing embedding models corrupts similarity scores silently — most common RAG bug.

pgvector Store

  • PostgreSQL + pgvector extension
  • Persistent across restarts (unlike FAISS)
  • SQL queryable — filter by source file, page, sheet
  • JSONB metadata per chunk

Nemotron 120B — Mixture of Experts

120B total parameters, only 12B active per inference. Quality close to a 120B model at the compute cost of a 12B one. At scale: you pay for active parameters, not total.

P2 — RAG Assistant

Key Design Decisions

Decision

pgvector over FAISS

FAISS is in-memory — disappears on restart, no SQL, no metadata filtering. pgvector lives inside Postgres: persistent, SQL-queryable, index-able, production-grade. Overkill for a demo; exactly right for production thinking.

Decision

ChatOpenAI, not ChatNVIDIA

LangChain's ChatNVIDIA wrapper threw constant warnings about temperature, frequency_penalty. ChatOpenAI with a custom base_url is OpenAI-compatible, accepts all params natively. Cleaner logs, no suppressed errors, same API.

Decision

mkstemp, not NamedTemporaryFile

Windows holds an exclusive lock on NamedTemporaryFile even after the with block exits. mkstemp() gives explicit fd control — close the fd first, then pass the path to pandas/PyPDF. This fixed the WinError 32 on Excel uploads.

Decision

vertexai stub over version pin

RAGAS hard-imports a LangChain module removed in v0.3+. Pinning the version downgraded langchain-core and broke P2. Fix: inject a fake module into sys.modules before any RAGAS import. No version constraint needed.

Dependency conflict lesson: Installing P3's RAGAS package downgraded langchain-core and broke P2's ModelProfile import. Same problem hits production microservices with shared venvs. The right fix: isolation (separate venvs / containers). The quick fix: stub what you don't need.

P2 — RAG Assistant

4 Live Prompt Strategies

Switchable from the settings sidebar. Same question, different prompt — answer changes instantly.

v1Very Strict

Only from context. Refuses anything not explicitly stated. Best for compliance — zero hallucination risk.

Prompt says: "NO OUTSIDE KNOWLEDGE. NO INFERENCE. NO ASSUMPTIONS."

v2Moderate

Interprets questions charitably. If inferable, it answers. Good for helpdesk bots and general Q&A.

Prompt says: "Interpret questions charitably. Only refuse when topic is genuinely absent."

v3Few Shot

3 worked Q→A examples before the real question. Model learns answer format and refusal behaviour from examples.

Includes one refusal example so model learns when NOT to answer.

v4Role Based

Model is a "senior knowledge management specialist." Role priming improves precision and professional tone.

Prompt says: "Meticulous, authoritative, only state what documents explicitly say."

For the demo: ask "How many days of annual leave do employees get?" with v1, then switch to v4. Same model, same document, same question — answer changes tone and depth instantly. This is the fastest way to explain prompt engineering live.

Why unanswerable questions matter

If you ask "When was Acme Corp founded?" and no document has that, the correct answer is a refusal. If the system fabricates an answer — that's the most dangerous failure mode. Refusal accuracy is the only metric that catches it.

💾
Crash-safe checkpointing

After each expensive phase, state is written to results/.checkpoint.json. On re-run, completed phases are skipped. RAGAS makes dozens of API calls — if it crashes, you don't re-pay for Phase 1 or 2. On success, checkpoint is deleted.

P3 — RAG Quality Gate

Judge Model: Why a Different One?

Self-serving bias — the failure mode

  • Generator gives a vague non-answer (its own hallucination pattern)
  • Same-model judge: sees familiar pattern → scores it 4/5
  • Independent judge: reads claim against context → scores it 2/5
  • Internal eval says PASS. Production says FAIL

gpt-oss-20b — why specifically

  • Different model family (OpenAI OSS ≠ NVIDIA Nemotron)
  • Reasoning model — generates chain-of-thought before scoring
  • reasoning_content visible — you see why, not just the score
  • Requires temperature=1, top_p=1 — reasoning model constraint

Honest trade-off table

ProsCons
No self-serving bias Extra API cost per eval run
Catches systematic generator errors Reasoning model is slower (chain-of-thought)
Industry standard (how GPT-4 evaluates smaller models) Judge also has its own biases — just less correlated
Reasoning chain = explainable scores Two model endpoints needed
"Eval runs happen before you ship, not on every user query. The extra cost is a quality-gate investment — a few API calls to confirm readiness vs. shipping a broken RAG system and losing user trust."

Diagnosis & Fix

Failing MetricRoot CauseFix
Context Precision
0.625 vs 0.70		 Chunking — top_k=4 returns noisy chunks mixed with relevant ones. Recall=1.0 proves the right chunk is there; precision fails because 3 extra chunks dilute it. Reduce top_k 4→2 and tighten chunk size 500→300 chars
Answer Relevancy
0.646 vs 0.70		 RAGAS requests 3 LLM variations to compute similarity — the reasoning model (gpt-oss-20b) only returns 1. Fewer samples = noisier cosine sim score. Use a non-reasoning model for RAGAS judge or switch to a direct relevancy prompt

What passed (and why it matters)

Recall = 1.0 — the retriever always finds the relevant chunk.
Faithfulness = 0.938 — the LLM stays grounded, minimal hallucination.
Refusal = 1.0 — all 4 unanswerable questions correctly refused.

Cross-Cutting

Fallback & Resilience

Implemented
  • Exponential backoff (P1 & P3) — 3 retries at 1s/2s/4s, covers API rate-limit spikes
  • Crash-safe checkpointing (P3) — saves after each phase, auto-resumes on re-run
  • Model via .env (all) — swap model without touching code
  • Global exception handler (P2) — all errors return clean JSON 500, never raw HTML
  • Pydantic validation — malformed LLM output fails fast, never propagates silently
  • /health endpoint (P2) — liveness check, integrates with load balancer probes
Production Additions
  • Circuit breaker — after N consecutive failures, stop calling, return degraded response
  • Model fallback chain — primary fails → try secondary model, degrade gracefully
  • pgvector replica — primary/replica config for HA; single Postgres is a SPOF
  • End-to-end timeout budget — deadline enforced at HTTP layer, not just LLM call
  • Dead letter queue — failed ingestion jobs retried async, not dropped

Real incident: NVIDIA deprecated llama-3.1-8b mid-project with 502 errors and no warning. Because the model was in .env, the fix was: change one variable, restart. Zero code change. That's why model config must never be hardcoded — deprecations are config changes, not emergencies.
